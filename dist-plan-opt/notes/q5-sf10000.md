## Why /scratch looked ~7 s slower: mostly GPFS drift, ~2-4 s real

All /scratch warm times measured today, in run order:

| Build | Warm times (s) |
|---|---|
| dist-plan-opt | 44.6, 42.8, 44.8, 43.5-44.2 |
| v3 | 36.5, 42.2, 41.4-42.4 |

The 36.5 s v3 run was a fast GPFS window. In the A/B pair with network sampling (`net-v3`, `net-dpo`,
run back to back) v3 is 41.4 s and dist-plan-opt 43.5 s.

Measured (Quent telemetry per pipeline, `tools/pipelines.py`; GPFS ingress from the RoCE NIC
counters, `scripts/netsample.sh` + `tools/netrate.py`):

- Q5 on /scratch is GPFS-bound in both builds: each warm run reads 1.22 TB, peaking ~40 GB/s and
  averaging 28-29 GB/s. Host CPU is 15-35 of 144 cores.
- The first ~4-10 s read almost nothing: the small scans (nation, supplier, region, customer, orders)
  run one after another, each behind an exchange. How long this takes varies by run (lineitem began
  at 6.0 s and 11.8 s in the first two runs, and at 10.1 s in both builds in the matched pair). It is
  GPFS latency, not the build.
- Then the lineitem scan is ~85% of the query. Every rank reads the same 453 GB (decoded) in the same
  522 batches, but rank 0 is the straggler in both builds:
  - v3: ranks 0 and 2 end at 40.4 and 41.2 s; ranks 1 and 3 at 32.8 and 33.5 s.
  - dist-plan-opt: rank 0 ends at 43.1 s, the others at 36.7-38.6 s.
  The query ends with the slowest rank, while GPFS ingress falls to ~12 GB/s with one rank left.
- Ruled out: dynamic filters (same merged 75M-row customer and 113M-row orders filters in both),
  broadcast joins (only the tiny region/nation builds are broadcast), memory-pressure downgrades
  (same in both, and only once the lineitem stage starts), and the RMM 10 MiB pool errors (in both).

So the remaining 2-4 s is in the lineitem stage, where per-rank GPFS throughput sets the time. The
plan doesn't change what each rank reads. In the cached runs, where I/O is free, dist-plan-opt is
32% faster (its per-rank skew is also smaller: 1 slow rank vs 2 for v3).

Open at the time: why rank 0 reads GPFS slower than the others. Answered in
[sf10k-improvements.md](sf10k-improvements.md): not NIC/NUMA but CPU pinning; ranks 0 and 2 ran
all their I/O threads on one core. Fixed in `432a7c88`.
