Timing. Unpinned runs every query in its own 4 processes, twice: the first run reads everything from GPFS (cold), the second runs in the same processes (warm). Pinned starts 4 processes once, pins the tables (51 s, not in the totals), then runs every query twice. Its cold run is a query's first run after pinning, in processes that already ran the earlier queries. From startup, one full pass takes 51 + 283 ≈ 334 s pinned against 807 s unpinned. Running all queries in one process is itself about 11% faster on queries that read no pins, so part of the warm gain comes from that, not from the pins.

What Pinned holds. 153 GB per rank in host memory, compressed: lineitem {l_orderkey, l_suppkey, l_commitdate, l_receiptdate}, orders (all columns the queries read except o_comment), partsupp and supplier as each rank's share, nation and region on every rank. Everything else is read from disk. With partial pin serving, a scan whose pin holds at least 30% of its columns (by width) reads those from the pin and the rest from disk; seven queries do (partly).

Answers. Both runs return the same answer as a reference unpinned run, row for row, numbers within 1e-6 relative or 0.01 absolute. Q3 and Q18 (Consistent*) differ only in tied rows past their ORDER BY columns, in both runs alike.

How to reproduce

Hardware and data. One host with 4× NVIDIA GB200 (189 GB each), 144 Grace cores on 2 NUMA nodes of 478 GB. TPC-H SF10000 Parquet from tpchgen-rs (3.7 TB) in /scratch/sirius/datasets/tpch_sf10000 on GPFS, read with O_DIRECT.

Build, both runs. Branch perf/sf10k-pinned-repro on aocsa/sirius, at 1af4e21b: dist-plan-opt-rank-pin (626fe147) plus two commits, the small-read cap (7c99ebe1) and partial pin serving (1af4e21b). Both runs use this one build; the configs below choose what each run uses.

git clone -b perf/sf10k-pinned-repro git@github.com:aocsa/sirius.git && cd sirius
git submodule update --init --recursive
pixi run make

1. Pinned

pinned.yaml:

sirius:
  memory:
    host: { capacity_bytes: 190Gi , downgrade_trigger_fraction: 0.97, downgrade_stop_fraction: 0.93 }
    disk: { disk_id: 0, capacity_bytes: 15000000000, downgrade_root_dirs: "@SPILL_DIR@" }
  executor:
    scan_manager:
      num_threads: 32
      uring_n_reactors: 4
      cache: { mode: none }
      uring: { max_inflight_small_reads: 16, small_read_bytes: 4MiB }
      pin_partial_serving: true
      pin_partial_min_fraction: 0.3
  operator_params:
    max_dynamic_filter_bloom_bytes_per_gpu: 4Gi

Pin once, then run all 22 queries twice in the same 4 processes:

pixi run python bench/dist-tpch/run_suite.py --out OUT --tag _pinned \
  --config pinned.yaml --host-pool 190Gi \
  --data /scratch/sirius/datasets/tpch_sf10000 --sf 10000 --iters 2 \
  --pin-tier host --pin-plans PLANS_DIR \
  --pin-only lineitem,orders,partsupp,supplier,nation,region \
  --pin-replicate nation,region \
  --pin-exclude l_partkey,l_quantity,l_extendedprice,l_discount,l_tax,l_returnflag,l_linestatus,l_shipdate,l_shipinstruct,l_shipmode,o_comment

PLANS_DIR holds the Simpatico plan files lineitem.txt, orders.txt, partsupp.txt and supplier.txt: the repo's src/compression/simpatico_codegen/plans/tpch_sf1000 files, with partsupp_disabled.txt and supplier_disabled.txt renamed. Results go to OUT/results.jsonl.

2. Unpinned

unpinned.yaml:

sirius:
  memory:
    host: { capacity_bytes: 210Gi }
    disk: { disk_id: 0, capacity_bytes: 30000000000, downgrade_root_dirs: "@SPILL_DIR@" }
  executor:
    scan_manager:
      num_threads: 32
      uring_n_reactors: 4
      cache: { mode: none }
      uring: { max_inflight_small_reads: 16, small_read_bytes: 4MiB }
  operator_params:
    max_dynamic_filter_bloom_bytes_per_gpu: 4Gi

Each query in its own 4 processes, twice:

for q in $(seq 1 22); do
  pixi run python bench/dist-tpch/run_query.py $q --out OUT/q$q \
    --config unpinned.yaml --host-pool 210Gi --sf 10000 --ranks 4 --iters 2 \
    --data /scratch/sirius/datasets/tpch_sf10000 --tag _direct
done

Partial pin serving stays off (the default), and nothing is pinned. Each query's times go to OUT/q<N>/results.jsonl.

Both. Empty the spill directory before each run, and check that no other Sirius process holds the GPUs. Times are DuckDB's timer on rank 0; run_suite.py and run_query.py take cold as the first run and warm as the second.
