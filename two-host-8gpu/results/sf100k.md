# TPC-H SF100000, the 5 queries without lineitem, on 8 GPUs across gcn-17 + gcn-18

**Outcome:** Q2, Q11, Q13, Q16 and Q22 all pass.

- **Answers:** both runs agree, and every sanity check passes. No reference answers exist at
  SF100000.
- **Spill:** Q2, Q11, Q16 and Q22 run in 2.4–3.4× their SF30000 time on 3.33× the data, with no
  spill.
- **Q13 is the exception:** 815 s cold, 622 s warm (about 20× SF30000).
  - It filled every GPU and host pool.
  - It spilled 2.9 TB to disk.

**Timings are not clean.** `tpchgen-cli` was generating SF100000 `lineitem` on gcn-18 during the
whole run: 64 threads, about 45 cores, about 2 GB/s of writes to the same GPFS.

### Answer checks

No SF100000 reference answers exist. [`sanity_sf100k.py`](../scripts/sanity_sf100k.py) checks facts
of the data instead ([sf100k-sanity.txt](sf100k-sanity.txt)).

- **Q13:** `custdist` must sum to the customer count, SF × 150,000 = 15,000,000,000. It does,
  exactly, in both runs.
- **Q2:** 100 rows.
- **Q16 and Q22:** within 2% of 10/3 × the SF30000 8-GPU answers. The data is uniform random, so
  these scale almost exactly.
- **Q11:** within 2% of 10/3 × SF30000's rows above the exact threshold.
  - The SF30000 query text rounds Q11's fraction 0.0001/SF to 0.0000000033, 1% below the exact
    value, so more parts qualify there.
  - SF100000's text uses the exact 0.0000000010.
  - SF30000 has 28,120,291 rows above the exact threshold; × 10/3 = 93,734,303, and SF100000 has
    93,496,926 (−0.25%).
  - Against SF30000's 29,971,985 rows, it looks 6.4% short.
- **Run 2 vs run 1:** Q11's ~93M rows are compared by row count plus an order-independent
  checksum of the lines. The other queries are compared row by row.

### Q13: why it is slow

- **Customers per rank:** Q13 groups all 15 billion customers, about 1.9 billion per rank.
- **GPU memory:** all 8 GPUs sat at 188 GB for most of the run.
  - Tasks of pipeline 6 reserved about 145 GB each and hit out-of-memory at `PARTITION` and
    `CONCAT` thousands of times.
  - Each task was rescheduled, at most 10 of the 100 allowed retries.
- **Host memory:** each rank's 180 GiB host pool stayed full.
- **Spill speed:** host→disk spill ran at about 450 MB/s per rank on GPFS, alongside the
  generator's writes.
- **SF30000 comparison:** at SF30000, Q13 peaked at 36 GiB of host pool per rank and did not
  spill. Its memory does not scale linearly from there.
- **Next step:** understand pipeline 6's 145 GB reservations, rather than more time or config.
  Rerunning once the generator is done would also show how much the shared GPFS cost.

## Setup

The same as the SF30000 run ([sf30k.md](sf30k.md)), with these differences:

- **Data:** `/scratch/prestouser/aocsa/tpch_sf100000`.
  - `part`, `supplier`, `partsupp`, `customer`, `orders`, `nation` and `region` were complete,
    with exactly 3.33× the SF30000 file count and size.
  - Key types are the same as SF30000 (BIGINT customer, order and part keys).
  - `lineitem` was still being generated and was not read.
- **Sirius config:** unchanged, p180 ([../configs/p180.yaml](../configs/p180.yaml): 180 GiB host pool, 1 TB
  disk cap per rank, spill per host on `/scratch`).
- **Per-rank timeout:** 7,200 s (3,600 s at SF30000).
- **No lineitem:**
  - `gen_sql.py` makes views only for the tables a query names.
  - At SF100000 it refuses any query that reads `lineitem`.
  - Q13 ran just before this change, so its `q.sql` also defines an unqueried `lineitem` view.
    DuckDB read only that glob's schema.
- **Build:** branch
  [`distributed-exchange-cross-node-tcp-lanes`](https://github.com/aocsa/sirius/tree/distributed-exchange-cross-node-tcp-lanes)
  at `5bc904c9`.
- **Ranks, exchange and environment:** as at SF30000.
  - 8 ranks, ports 27200–27207.
  - TCP lanes across hosts, NIXL over NVLink within a host.
  - `UCX_NET_DEVICES=bond0`.
  - Each query directory keeps its `sirius-<host IP>.yaml`, `env-<host>.txt`, `q.sql` and
    `launch.txt`.

## Reproduce

From gcn-17, with the same prerequisites as SF30000 ([sf30k.md](sf30k.md#reproduce)):

```bash
cd two-host-8gpu/scripts
export PATH=$HOME/.pixi/bin:$PATH
unset AI_AGENT CLAUDECODE CLAUDE_CODE CURSOR_AGENT
./run_sf100k.sh ../runs/sf100k 13 2 11 16 22     # NUMA guards on both hosts, 2 runs per query
python3 sanity_sf100k.py ../runs/sf100k           # the answer checks above
python3 mem_stats.py ../runs/sf100k/q13           # spill and host-pool peak per host
```

- **SF30000 answers:** `sanity_sf100k.py` needs them in `../refs/sf30k/` (or `REF_DIR`); the
  8-GPU run's are equivalent.
- **Raw run directory** (not in git): `/scratch/prestouser/aocsa/bench-xnode/tpch2host/runs/sf100k/`.
- **Results in this repo:** [sf100k-results.jsonl](sf100k-results.jsonl) and
  [sf100k-sanity.txt](sf100k-sanity.txt).
